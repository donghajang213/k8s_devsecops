# ADR 0001: Postgres를 StatefulSet이 아니라 Deployment로 배포

## 상태
승인됨 (의도적 단순화)

## 배경
클러스터 내부에 Postgres를 하나 띄워야 했다. K8s에서 상태를 갖는 워크로드(DB 등)의 정석은
StatefulSet이다 — 파드마다 고정된 이름/네트워크 ID, 레플리카별 전용 PVC(`volumeClaimTemplates`),
순서 보장 기동/종료를 제공한다.

## 결정
`replicas: 1`인 단일 인스턴스이므로 Deployment + 별도 PVC 하나로 구성했다.

## 근거
- StatefulSet의 이점(레플리카별 고유 PVC, 순번 기반 네트워크 identity, 순차 기동)은
  레플리카가 여러 개일 때 의미가 있다. 지금은 인스턴스가 하나뿐이라 이 이점을 실질적으로
  못 쓴다.
- 대신 실제로 겪은 문제가 있다: `Deployment`의 기본 롤링 업데이트 전략은 새 파드를 먼저
  만들고 이전 파드를 나중에 지우는데, `ReadWriteOnce` 볼륨은 동시에 두 파드가 못 붙는다.
  새 파드가 볼륨을 못 붙여 `Ready`가 안 되고, 그래서 이전 파드도 안 지워지는 교착 상태가
  실제로 발생했다. `strategy.type: Recreate`(기존 파드를 완전히 지운 뒤 새로 만듦)로
  해결했다.

## 트레이드오프
- 무중단 배포는 원래도 단일 DB 인스턴스에서는 의미가 없으므로 손해가 아니다.
- 나중에 레플리카를 늘리게 되면(리드 레플리카 등) 이 결정을 StatefulSet으로 재검토해야 한다.
- 정석(StatefulSet)을 몰라서가 아니라, 지금 구성(단일 인스턴스)에서는 실익이 없어 의도적으로
  단순화했다는 것을 분명히 해둔다.
